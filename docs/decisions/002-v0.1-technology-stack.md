# ADR-002: Loren v0.1 Technology Stack

- **Status:** Proposed — accept after Milestone 0 technical validation
- **Date:** 2026-09-03
- **Decision owners:** Loren project

## Context

ADR-001 established that Loren owns identity, canonical state, memory, policy, action authorization, and audit history. The remaining question is how to implement the first useful version without introducing a large agent framework that would duplicate Loren's core responsibilities.

The v0.1 stack should optimize for:

1. deterministic control of the model/tool loop;
2. easy implementation of the Loren Action Gateway;
3. first-class MCP support without making MCP the domain model;
4. low operational complexity for a one-owner/self-hosted system;
5. strong typing and testability;
6. isolation of unstable/provider-specific SDK surfaces behind adapters.

## Proposed decision

### Language/runtime

- **C# 14 / .NET 10 LTS**
- **ASP.NET Core** as the host

### Brain

- **OpenAI Responses API** as the initial reasoning provider
- official `openai-dotnet` SDK
- Loren-defined `IBrain` boundary around the provider

Conceptual contract:

```csharp
public interface IBrain
{
    Task<BrainTurnResult> ThinkAsync(
        BrainContext context,
        IReadOnlyList<ActionDefinition> availableActions,
        CancellationToken cancellationToken);
}
```

The provider returns text/reasoning outputs and structured action requests. It does not directly own authorization or privileged execution.

### Agent runtime

Use a **small Loren-owned agent loop**, not LangChain, Semantic Kernel, OpenClaw, Letta, or another broad orchestration framework for v0.1.

Conceptual loop:

```text
prepare context
    -> call brain
    -> receive final output OR ActionRequest
    -> validate ActionRequest
    -> Action Gateway / approval
    -> controlled executor
    -> structured ActionResult
    -> feed result back to brain
    -> repeat within bounded limits
```

The loop must have hard limits for turns/tool calls/cancellation and must be testable with a fake `IBrain`.

### MCP

- use the official **Model Context Protocol C# SDK** for MCP client integration where useful;
- prefer the smallest package surface needed (`ModelContextProtocol.Core` when sufficient);
- normalize MCP tools into Loren `ActionDefinition` / `ActionRequest` / `ActionResult` contracts;
- do not expose privileged remote MCP tools directly to the model through provider-managed remote-MCP execution when that would bypass Loren's Action Gateway.

MCP is an integration transport. Loren may also use direct vendor APIs for capabilities where that is simpler or safer.

### Persistence

- **SQLite** for canonical v0.1 state
- **Entity Framework Core** for schema/migrations

Initial storage needs are single-owner, low-throughput, and local/self-hosted. A server database is not justified until real concurrency/scale requires it.

### UI

- **Blazor Web App** hosted with ASP.NET Core for v0.1
- prioritize a single deployable stack and low moving-part count over frontend specialization
- UI remains replaceable; no domain or runtime logic belongs in Blazor components

### Testing

- xUnit for unit/integration tests
- fake `IBrain`, fake executors, and deterministic policy tests
- real-provider/MCP/GitHub tests separated from deterministic core tests

## Important SDK stability note

As of the 2026-09-03 planning snapshot:

- .NET 10 is an LTS release;
- the official MCP C# SDK is a Tier 1 SDK;
- OpenAI's .NET Responses client supports Responses/function-calling and MCP-related APIs, but parts of the Responses surface are still marked experimental in the SDK.

Therefore v0.1 must pin exact package versions and keep provider/MCP SDK types behind adapters. No experimental/provider-specific type may become a Loren domain type.

## Milestone 0 validation before acceptance

Before changing this ADR to **Accepted**, create disposable technical spikes that prove:

### Brain spike

- call the selected OpenAI model through Responses API;
- expose a Loren-defined function/action schema;
- receive a structured function/action request;
- execute a fake action through Loren code;
- return the structured result and receive a final response;
- cancel a run;
- enforce a bounded tool/turn limit;
- verify no API key/tool credential appears in model-visible context or logs.

### MCP spike

- connect to one harmless MCP server using the official C# SDK;
- enumerate/normalize tool metadata into Loren action definitions;
- invoke one read-only MCP tool through Loren's executor path;
- prove MCP SDK types do not cross into `Loren.Core`.

### Persistence spike

- create SQLite database through EF Core migration;
- persist and reload a minimal Owner/Project/Audit record;
- perform an export/restore smoke test at the storage boundary.

### Web-host spike

- run ASP.NET Core + minimal Blazor page;
- execute one fake brain request end to end through DI/cancellation/logging.

## Acceptance criteria for ADR-002

Accept this stack if all of the following are true:

- the custom loop is small and understandable rather than becoming a framework project;
- OpenAI tool/function calls can be intercepted before every side effect;
- provider credentials and tool credentials can remain separated;
- official MCP client integration works behind Loren abstractions;
- SQLite/EF Core satisfies canonical-state/recovery requirements for v0.1;
- the full host can run locally with a small operational footprint;
- no experimental SDK surface leaks into Loren.Core.

If one area fails, replace only that adapter/component rather than reopening ADR-001.

## Proposed solution layout

```text
src/
├── Loren.Api/              # ASP.NET Core host/API
├── Loren.Core/             # domain, memory contracts, policy/action contracts
├── Loren.Runtime/          # context builder + thin agent loop
├── Loren.Brain.OpenAI/     # OpenAI Responses adapter
├── Loren.Tools/            # action registry/executors
├── Loren.Tools.Mcp/        # MCP adapter
├── Loren.Tools.GitHub/     # GitHub capability
├── Loren.Infrastructure/   # EF Core, SQLite, secrets, audit persistence
└── Loren.Web/              # Blazor UI

tests/
├── Loren.Core.Tests/
├── Loren.Runtime.Tests/
├── Loren.IntegrationTests/
└── Loren.E2E.Tests/
```

The exact project count may be reduced during scaffolding if this creates unnecessary ceremony. Dependency direction matters more than folder count.
