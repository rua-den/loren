# ADR-002: Loren v0.1 Technology Stack

- **Status:** Proposed — M0 provider-neutral live brain proof in progress
- **Date:** 2026-09-03
- **Decision owners:** Loren project

## Context

ADR-001 established that Loren owns identity, canonical state, memory, policy, action authorization, context assembly, and audit. Model providers, MCP servers, vendor APIs, UI clients, and execution infrastructure are replaceable adapters.

ADR-002 selects the implementation stack for v0.1 without allowing one provider SDK or billing account to become Loren's identity or security boundary.

The stack should optimize for:

1. deterministic control of the model/tool loop;
2. a small Loren-owned Action Gateway;
3. replaceable brain providers behind one domain contract;
4. MCP support without making MCP the domain model;
5. low operational complexity for one-owner/self-hosted use;
6. strong typing and deterministic tests;
7. provider credentials isolated from tool credentials and canonical state.

## Proposed decision

### Language and host

- **C# 14 / .NET 10 LTS**
- **ASP.NET Core** host
- **Blazor Web App** for the initial owner UI

### Brain boundary

Loren owns a provider-neutral `IBrain` contract. No provider-specific type may cross into `Loren.Core`.

Conceptual contract:

```csharp
public interface IBrain
{
    Task<BrainTurnResult> ThinkAsync(
        BrainContext context,
        IReadOnlyList<ActionDefinition> availableActions,
        CancellationToken cancellationToken);
}
```

Initial adapters may include:

```text
Loren.Brain.Ollama
Loren.Brain.OpenAI
future providers / local models
```

A configured provider receives prepared context and Loren-defined action schemas. It may return reasoning/text and structured action requests. It may not authorize or directly execute privileged actions.

### Agent runtime

Use a **small Loren-owned bounded agent loop**, not a broad orchestration framework for v0.1.

```text
prepare BrainContext
    -> IBrain
    -> final output OR ActionRequest
    -> Loren ActionGateway
    -> policy / approval
    -> controlled executor
    -> ActionResult
    -> IBrain
    -> bounded repeat
```

Hard turn/tool/cancellation limits belong to Loren and must be deterministic/testable with fake brains.

### MCP

- official MCP C# SDK behind a Loren adapter;
- normalize MCP tools into Loren action contracts;
- MCP is transport/integration, not Loren's canonical skill or permission model;
- provider-managed remote MCP must not bypass the Action Gateway.

### Persistence

- **SQLite** canonical store for v0.1;
- **Entity Framework Core** migrations/schema access;
- provider/runtime conversation IDs are never canonical identity.

### Testing

- **xUnit** for deterministic core/runtime tests;
- fake brains/executors for policy and loop behavior;
- live provider/MCP/GitHub tests separated from deterministic core CI.

## Why the brain gate is provider-neutral

M0 initially used OpenAI Responses as the first live candidate. The repository secret path and provider reachability were proven, but the live request was rejected before model execution with:

```text
HTTP 429
insufficient_quota: credit_balance_exhausted
```

That is a vendor billing state, not evidence that Loren's architecture is invalid.

Requiring OpenAI specifically would contradict ADR-001 and Loren's core principle:

> **Model is replaceable compute. Loren is stateful identity.**

Therefore Gate B now requires **at least one real brain provider** to prove the complete Loren-controlled action loop and cancellation boundary. Other providers can remain supported adapters even when they are not the provider used to close M0.

## M0 acceptance proof

Before changing this ADR to **Accepted**, M0 must prove:

### Real brain provider

At least one configured provider must complete:

```text
real provider
 -> structured get_project_status ActionRequest
 -> Loren ActionGateway
 -> fake/read-only executor
 -> structured ActionResult
 -> real provider
 -> final answer
```

And:

- hard six-turn bound is enforced by Loren;
- cancellation terminates through the provider call;
- PASS is impossible unless an action crossed the gateway;
- provider secret is not emitted in logs or action payloads.

### MCP

- official MCP C# client connects to a harmless server;
- tool metadata is normalized into Loren-owned shapes;
- one allow-listed read-only action executes through Loren code;
- MCP SDK types remain adapter-local.

### Persistence

```text
EF migration
 -> persist canonical sample state
 -> export
 -> wipe
 -> migrate fresh DB
 -> restore
 -> reload/verify
```

### Web host

- ASP.NET Core + Blazor boots;
- health endpoint works;
- fake brain resolves through DI;
- cancellation/logging reaches the brain boundary.

## M0 evidence — 2026-09-03

Disposable evidence lives under `spikes/adr-002/` and is not production architecture.

### OpenAI adapter evidence

Validated:

- `.NET 10` build with official `OpenAI` package `2.12.0`;
- Responses function/action request intercepted by Loren-owned code;
- provider function arguments parsed/validated before fake execution;
- hard turn bound and cancellation plumbing compile cleanly;
- repository secret is available only through trusted live validation and is masked in logs;
- trusted request reaches OpenAI's provider endpoint.

Current provider-specific limitation:

```text
OpenAI model execution -> BLOCKED by credit_balance_exhausted
```

This does not block a different `IBrain` adapter from satisfying Gate B.

### Ollama adapter evidence

PR #6 adds a native Ollama Cloud spike using:

```text
POST https://ollama.com/api/chat
Authorization: Bearer $OLLAMA_API_KEY
model: gpt-oss:120b
```

The implementation:

- has no Ollama vendor SDK dependency;
- exposes `get_project_status` using Ollama's native tool schema;
- receives `message.tool_calls`;
- validates and executes the request only through Loren `ActionGateway` code;
- appends the assistant tool-call message plus a `role=tool` result;
- requires the provider to return final content after observing the result;
- has the same six-turn bound;
- supports explicit provider-call cancellation.

PR #6 no-secret CI currently proves:

```text
OpenAI spike build              PASS
Ollama spike build              PASS
MCP regression                  PASS
SQLite/EF recovery regression   PASS
ASP.NET/Blazor regression       PASS
live secret steps               SKIPPED in PR by design
```

After merge, trusted live validation prefers Ollama when `OLLAMA_API_KEY` exists, otherwise OpenAI when `OPENAI_API_KEY` exists, otherwise it fails closed.

### MCP evidence

Validated with `ModelContextProtocol` `2.2.0` and pinned reference server `@modelcontextprotocol/server-everything@2026.8.31`:

- real stdio connection;
- 13 tools enumerated/normalized;
- only allow-listed `echo` executed;
- SDK types stayed inside adapter/spike boundary.

### Persistence evidence

Validated with EF Core SQLite `10.0.11`:

```text
migration -> persist -> export -> wipe -> migrate -> restore -> reload
```

### Host evidence

Validated:

- ASP.NET Core / Blazor build on .NET 10;
- `/health` works;
- Blazor root renders;
- fake brain resolves through DI;
- request cancellation and logging are available at brain boundary.

## Acceptance criteria

Accept ADR-002 when all are true:

- the Loren-owned loop remains small and understandable;
- at least one real provider completes action request -> gateway -> result -> final response;
- live cancellation works through that provider boundary;
- all side effects remain interceptable before execution;
- provider/tool credentials remain separate;
- MCP works behind Loren abstractions;
- SQLite/EF satisfies v0.1 canonical-state/recovery needs;
- host remains operationally small;
- no provider/MCP SDK type leaks into `Loren.Core`.

A provider-specific failure should replace/fix only that adapter or model choice, not reopen ADR-001.
