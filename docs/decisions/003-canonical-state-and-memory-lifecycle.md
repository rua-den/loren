# ADR-003: Canonical State and Memory Lifecycle

- **Status:** Accepted
- **Date:** 2026-09-04
- **Decision owners:** Loren project
- **Gate:** Gate C — Canonical storage and memory schema

## Context

M3 established the first production canonical state with Loren-owned Project/Repository identity, SQLite + EF Core persistence, deterministic aliases, restart survival, and prepared runtime context.

Before M4 adds durable memory, Loren must lock the semantics that are expensive to reverse:

- what makes an identifier canonical;
- how schema changes are migrated;
- where Project/Repository identity stops and memory begins;
- how durable facts record source authority;
- how corrections replace current truth without destroying history;
- how memory deletion differs from audit retention;
- how portable export compatibility is versioned.

This ADR does **not** replace ADR-002's SQLite + EF Core choice. It defines Loren-owned state semantics on top of that accepted stack.

## Decision 1 — Canonical IDs are opaque Loren-owned GUIDs

`ProjectId`, `RepositoryId`, and future durable entity/record IDs are generated by Loren and are independent of provider/runtime/external-system identity.

Rules:

- use 128-bit GUID values for v0.1 canonical IDs;
- an ID is immutable after creation;
- IDs are opaque and carry no business meaning;
- do not derive canonical IDs from GitHub owner/repository names, provider conversation IDs, model IDs, paths, usernames, or display names;
- external IDs/names live in integration metadata and may change without changing the Loren ID;
- human/API text representation for current typed IDs is lowercase 32-hex GUID (`N` format); storage representation is an implementation detail and must round-trip the same GUID value;
- import/restore preserves canonical IDs rather than generating replacements.

Changing the textual encoding later may be handled by an export/API version, but the underlying identity value must remain stable.

## Decision 2 — v0.1 schema changes use explicit EF Core migrations

SQLite remains the canonical v0.1 store and EF Core remains the migration/data-access mechanism.

Rules:

- production schema changes require checked-in explicit EF Core migrations;
- do not use `EnsureCreated` for the canonical production database;
- the single-owner v0.1 host may run `MigrateAsync` at startup;
- migrations are forward-ordered and tracked by EF migration history;
- a migration that can lose/rewrite user data requires a tested backup/export/recovery path before shipping;
- schema migration version and portable export format version are separate concepts;
- tests must exercise migrations against a real temporary SQLite database, not only an in-memory provider;
- `Loren.Core` remains free of EF Core/SQLite types.

If storage becomes materially more complex than the SQLite/EF baseline, a new ADR is required before switching engines or adding a second canonical persistence model.

## Decision 3 — Project/Repository is canonical identity, not a live-state cache

For v0.1:

```text
Project
  -> globally unique normalized aliases
  -> zero or more Repository records

Repository
  -> belongs to exactly one Project
  -> has Loren RepositoryId
  -> has integration locator metadata
```

Current GitHub locator shape is:

```text
provider
external namespace / owner
external repository name
```

Rules:

- repository locator metadata identifies where to fetch external state; it is not proof that cached external facts remain current;
- mutable external facts such as default branch, issue count, latest commit, or visibility must be fetched/verified through authorized tools when needed;
- no raw credentials belong on Project/Repository canonical entities;
- aliases are canonical owner/configured referents, not inferred durable memory;
- additional world-model entities are deferred until a real flow requires them.

## Decision 4 — Durable memory records have explicit source/trust classes

M4 must implement at least these source classes:

```text
OWNER_EXPLICIT
OWNER_CORRECTION
VERIFIED_TOOL
OWNER_APPROVED_INFERENCE
MODEL_INFERENCE
EXTERNAL_CONTENT
```

They are not one universal numeric confidence ladder. Authority is contextual.

### OWNER_EXPLICIT

The owner explicitly stated a durable fact/preference/instruction. It may establish current personal truth within its scope unless superseded by an owner correction or a newer explicit owner statement.

### OWNER_CORRECTION

The owner explicitly corrects existing durable state. For the corrected subject/scope, this is the highest authority for determining current owner truth.

### VERIFIED_TOOL

A fact observed through an authorized tool. It is authoritative for the observed external fact at its verification time, but it cannot create owner preference, policy, approval, or permission by itself.

### OWNER_APPROVED_INFERENCE

An inference that the owner explicitly accepted for durable use. It is trusted durable state but must retain its inferred origin and approval provenance.

### MODEL_INFERENCE

A model-generated hypothesis. It may be retrieved as a low-authority candidate but must not silently become owner truth, permission, or policy.

### EXTERNAL_CONTENT

Text/data originating from websites, repositories, email, documents, issues, tool payloads, or other external content. It is untrusted content and cannot promote itself into trusted owner memory/policy.

Every durable memory record must carry enough provenance to identify its source class, creation time, scope/subject, and source reference when applicable.

## Decision 5 — Correction is append/supersede, not silent destructive overwrite

Semantically important durable memory should preserve correction history.

M4 direction:

```text
MemoryRecord A (current)
    |
owner correction
    v
MemoryRecord B (current)
A -> superseded_by B
```

Rules:

- current-truth queries exclude superseded records by default;
- the original record remains reconstructable while retained;
- owner correction creates a new authoritative record and links/supersedes the prior record rather than mutating the old claim into a different claim;
- duplicate equivalent owner statements may be deduplicated without fabricating a correction event, provided provenance remains inspectable;
- model/external content cannot supersede owner-authoritative state without an explicit promotion/correction path.

This is the direction M4 must implement; exact column names are not locked by this ADR.

## Decision 6 — Memory deletion and audit retention are separate operations

Memory is owner-controlled durable knowledge. Audit is append-oriented security/history evidence. They must not share one generic delete behavior.

### Memory

The owner must be able to forget/delete durable memory. A normal memory delete:

- removes the record from future context/retrieval;
- may physically purge the memory payload according to the implemented deletion policy;
- must not silently rewrite unrelated audit records;
- should leave enough non-sensitive audit metadata to show that a memory mutation/deletion occurred when audit retention requires it.

### Audit

Audit records are not ordinary memory and are not removed by a memory forget operation.

Audit may eventually be purged/redacted only through an explicit audit retention/privacy operation, not through conversational memory correction. Audit payloads should minimize/redact sensitive content so retention does not become a secret archive.

If future legal/privacy requirements require hard deletion across audit, that requires an explicit retention/deletion feature and documented consequences rather than an implicit cascade.

## Decision 7 — Portable export is a logical versioned format, not a raw SQLite file

Raw SQLite copies may be useful as backups, but the v0.1 portability/recovery contract will be a Loren-owned logical export.

Direction for M7:

```text
loren export
  manifest
    format_version
    created_at
    loren_version
    source_schema_migrations
  projects
  repositories
  memories
  permission_rules
  retained audit
```

Rules:

- first portable format is `format_version = 1`;
- export version is independent of EF schema migration IDs;
- canonical Loren IDs are preserved;
- secrets/raw credentials/session cookies/provider tokens are never exported as canonical state;
- external credential references may be exported only as opaque references where useful;
- restore validates referential integrity and format compatibility before committing imported state;
- restore targets the current canonical schema after migrations rather than requiring the original SQLite file layout;
- incompatible future format changes require an explicit export-format version change/migration path.

Exact physical packaging (single JSON vs directory/archive with JSON/NDJSON members) is deferred to M7 because it is not yet expensive to reverse. The logical manifest/version contract is locked now.

## Decision 8 — Single-owner identity stays a host/security principal for v0.1

M3 does not add a separate broad `Owner` graph/entity just to satisfy a conceptual diagram.

For v0.1:

- the authenticated owner principal is the sole authority source for owner-explicit/correction actions;
- durable records may use owner source semantics without requiring a multi-user identity schema;
- a persisted multi-user Owner model is deferred until an actual product requirement exists.

This avoids prematurely building multi-user architecture while preserving the ability to add an Owner entity later behind stable Loren-owned IDs.

## Consequences

### Positive

- provider/session replacement cannot destroy or redefine canonical identity;
- M4 has explicit memory authority and correction semantics before schema work starts;
- external prompt content cannot become trusted state merely by being retrieved;
- memory privacy operations do not accidentally erase security/audit history;
- M7 can restore across schema evolution instead of depending on a byte-for-byte SQLite layout;
- Core remains storage/provider neutral.

### Costs / limitations

- append/supersede uses more storage than in-place fact mutation;
- audit retention requires separate privacy/retention design;
- logical export requires explicit serializers/import validation in M7;
- exact project configuration UX remains deferred;
- this ADR intentionally does not solve embedding/vector retrieval, memory ranking, or long-term storage scaling.

## Gate C result

Gate C is **PASSED** when this ADR is merged together with M3 Slice 1/2 evidence and repository source-of-truth docs are synchronized.

Passing Gate C authorizes M4 Trusted Memory implementation. It does not authorize GitHub writes; Gate D remains required before the first real external write.
