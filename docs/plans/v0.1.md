v0.1 should feel like an actual personal secretary, not a collection of infrastructure components.

> **Loren must converse, remember, retrieve current information, research, organize and safely complete one approved action before broadening mutation scope.**

---

# 1. v0.1 objective

The owner should be able to keep Loren open and use it naturally throughout the day for:

```text
A. ordinary conversation / reasoning
B. current information lookup
C. project/personal context recall
D. research and synthesis with sources
E. notes / decisions / tasks
F. one explicitly approved consequential action
G. explanation / audit
H. restart continuity and recoverability
```

---

# 2. Required owner-visible flows

## Ordinary conversation

Stable questions should answer directly without unnecessary tools.

## Current information

Current questions should trigger read-only retrieval and return grounded sources rather than stale model guesses.

## Project context

Project questions resolve Loren-owned canonical Project/Repository identity, trusted memory and authoritative live reads when needed.

## Durable memory

Owner-explicit facts/corrections survive restart and obey provenance/correction/forget semantics.

## Research

Loren can search/fetch multiple bounded public sources, synthesize trade-offs and distinguish retrieved facts from inference.

## Personal organization

The owner can create/list/complete/reopen durable Notes, Decisions and Tasks through conversation. Background reminders are not part of v0.1.

## Approved action

```text
owner asks naturally
 -> Loren resolves canonical target
 -> exact proposal card
 -> owner explicitly approves
 -> Gate D one-time approval
 -> isolated credential-bound executor
 -> independent post-write verification
 -> natural result + audit
```

Current proof action: create a non-default GitHub branch from an exact frozen SHA.

## Continuity/recovery

Conversations/project scope survive restart; logical export/restore preserves Loren-owned state while revoking/cancelling executable authority as documented.

# 4. Current work — M6B Daily Driver Readiness

## M6B.1 — transient audit lifetime [COMPLETE]

The current-request audit collector is scoped instead of process-wide. Durable SQLite audit remains canonical.

## M6B.2 — safe readiness diagnostics [CURRENT DELIVERY]

Keep:

```text
GET /health
```

as public liveness.

Add owner-authenticated:

```text
GET /api/readiness
```

with secret-safe local diagnostics for:

- SQLite availability;
- project catalog/count;
- owner auth config;
- Ollama brain config validity;
- web search/fetch config validity;
- write mode;
- GitHub write credential state when enabled.

No external network call belongs in this endpoint. It is a configuration/state readiness report, not a provider SLA probe.

Read-only mode is the normal safe default and may return overall `ready` with `externalWrites=disabled`.

Tests must prove auth, liveness separation, missing/revoked write credential handling and no secret values in response bodies.

# 5. v0.1 non-goals

Not required for first release:

```text
voice/STT/TTS
native mobile app
Home Assistant
unrestricted shell/computer use
autonomous production deployment
multi-user architecture
multi-agent orchestration
standing write permissions
broad background autonomy
generic connector framework
controlled GitHub file/commit/open-PR expansion unless real use makes it highest value
```

---

# 6. Security and reliability gates

v0.1 must preserve:

- exact canonical IDs/targets;
- trusted memory provenance and anti-poisoning;
- authenticated private owner state;
- model/content inertness;
- exact one-time external approval;
- global read-only fail-closed state;
- credential isolation/revocation/redaction;
- independent external-write verification;
- durable retained audit;
- safe recovery semantics;
- bounded agent/tool loops;
- Windows SQLite/integration support.

Gate E is still required before any background scheduler/reminder delivery.

---

# 7. v0.1 release gate

Tag `v0.1.0` only when owner live proof and release review establish that:

- conversation is the primary useful surface;
- current/research behavior is grounded;
- memory/project/organization state survive restart correctly;
- continuity feels coherent;
- one consequential action works through explicit approval and exact verification;
- read-only and revocation stop writes;
- recovery works without exporting credentials;
- no material daily-use blocker remains;
- deterministic tests and cross-platform CI remain green.

---

# 8. After v0.1

Do not assume the next step is GitHub mutation expansion.

First v0.2 engineering question:

> Is Loren actually provider-portable, or only provider-neutral on paper?

Current answer: only provider-neutral on paper. Production host uses `OllamaBrain`; the OpenAI project is a stub.

Prove a second production brain adapter, then select one read-only personal-secretary integration—Calendar read/search is a strong first candidate. Let that vertical slice define the connector abstraction needed for later integrations.
