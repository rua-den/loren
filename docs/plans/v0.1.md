# Loren v0.1 — Trustworthy Core Implementation Plan

**Status:** Active — M3 Canonical State  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002

v0.1 is not a feature-rich assistant release. It is the first version where Loren proves that identity, memory, action authorization, credentials, audit, and external tool use fit together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Build the smallest Loren that can reliably complete four end-to-end flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete regardless of how many integrations exist.

---

# 2. v0.1 non-goals

Explicitly defer:

- broad web research;
- reminders/background scheduling;
- Gmail/Calendar;
- voice/wake word;
- native mobile apps;
- Home Assistant;
- unrestricted shell/computer use;
- autonomous production deployments;
- multi-user product architecture;
- multi-agent orchestration;
- plugin marketplace;
- generic agent-framework capabilities;
- dynamic multi-provider routing as a release requirement.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
                         |            |
                         |       provider adapter
                         |            |
                         +---- ActionRequest
                                   |
                                   v
                            Action Gateway
                           /      |       \
                      Policy  Approval   Audit
                           \      |       /
                            Executor Boundary
                                   |
                             Secret Resolver
                                   |
                           GitHub / MCP / APIs
```

Hard invariant:

> **The brain can request an action. Only Loren can authorize and execute it.**

Changing brain provider must not migrate Loren identity, memory, permissions, projects, or audit history.

# 8. Milestone 4 — Trusted memory

Implement continuity without an unstructured transcript dump.

Required source classes:

```text
OWNER_EXPLICIT
OWNER_CORRECTION
VERIFIED_TOOL
OWNER_APPROVED_INFERENCE
MODEL_INFERENCE
EXTERNAL_CONTENT
```

Trust rules: owner corrections supersede prior current truth; verified tool facts keep provenance/time; model inference is not owner truth; external content is untrusted and cannot silently create authoritative personal state.

Minimum capabilities include save, scope, provenance, inspect, correct/supersede, forget/delete, authority-aware retrieval, and small inspectable brain context. M4 exits only after restart, correction, and poisoning tests pass.

---

# 9. Milestone 5 — Action policy, credentials, and GitHub writes

First real side-effect boundary:

```text
Brain / Runtime
 -> ActionRequest (no secret)
 -> Action Gateway
 -> allow / deny / require approval
 -> Controlled Executor
 -> Secret Resolver
 -> GitHub
 -> post-verification
 -> Audit
```

v0.1 write scope remains narrow: create branch, create/update file/commit path, commit, and open pull request. Gate D must settle credential and approval binding/replay rules first.

---

# 10. Milestone 6 — Minimal daily-use UI

Required UI: conversation, active run/tool activity, exact approvals, current Project context, memory inspect/correct/delete, audit timeline, cancellation, and clear errors. M6 exits when all four required v0.1 flows work through the UI.

---

# 11. Milestone 7 — Recovery and state ownership proof

Export minimum includes owner continuity config, Projects/Repositories, durable memory/provenance, permission rules, retained audit, and schema/export version metadata. Secrets are excluded. Acceptance is export -> wipe -> restore -> restart with the same canonical behavior without provider/runtime sessions.

---

# 12. Milestone 8 — Security and reliability E2E

Cover restart continuity, aliases, memory correction/poisoning, GitHub grounding, authorized/approval-gated writes, denied destructive requests, prompt injection, approval replay, global read-only mode, duplicate/retry protection, stale-state checks, provider/tool failures, credential/log redaction, cancellation/turn limits, export/restore, and audit reconstruction.

---

# 13. v0.1 release gate

Tag `v0.1.0` only when all four release flows pass end to end and the memory/action/approval/recovery/security gates defined above are proven. CI/static checks must be green and known limitations documented.
