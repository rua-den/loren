---

# 1. v0.1 objective

Required flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren resolves canonical target
   -> policy requires exact owner approval
   -> approval is validated/consumed once
   -> controlled executor resolves write credential
   -> GitHub write
   -> deterministic post-write verification
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, canonical target,
      policy decision, approval, credential purpose,
      execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
      |                  |            |
      |                  |       provider adapter
      |                  |            |
      |                  +---- ActionRequest
      |                              |
      |                              v
      |                       Action Gateway
      |                      /      |       \
      |                 Policy  Approval   Audit
      |                      \      |       /
      |                       Executor Boundary
      |                              |
      |                        Secret Resolver
      |                              |
      |                        GitHub / MCP / APIs
      |                              |
      |                        Post-write verify
      |
      +--> Loren-owned canonical state
            Project / Repository
            Durable Memory + provenance
            Approval/permission state
            Audit history
```

Hard invariants:

> **The brain can request an action. Only Loren can authorize and execute it.**

> **The brain can consume prepared memory. It cannot silently promote model/external content into trusted owner truth or permission.**

> **Authentication proves owner identity. It is not write approval.**

> **A write is not successful until Loren verifies the intended external postcondition.**

# 9. Gate D — Action/Credential Policy [PASSED]

**Decision:** ADR-004 — Action Approval and Credential Boundary.  
**PR:** #24  
**Merge:** `b8649cb563e30af845a0b383103797632bed79a4`  
**Validation:** exact-head CI #164 / `33896004193` — Ubuntu full gate + Windows integration PASS.

Gate D locks the first write-capable policy contract before M5 executors exist.

## 9.1 Explicit action access/risk

Loren-owned classification:

```text
READ
REVERSIBLE_WRITE
EXTERNAL_WRITE
PRIVILEGED_WRITE
```

Authorization may not be inferred only from names or model text.

## 9.2 Canonical target binding

Before write authorization, Loren binds intent to:

```text
ProjectId
RepositoryId
provider/external locator snapshot
normalized target ref/branch/path/base/head fields
security-relevant parameters
trusted owner principal reference
```

Unknown/mismatched scope fails before credential resolution.

## 9.3 All first-version real writes require explicit owner approval

The first M5 write-capable implementation does not use standing permissions. Even reversible remote branch creation requires owner approval until the one-time path is proven.

Authentication/session identity is necessary but not sufficient.

## 9.4 Approval artifact + non-replay

Approval is Loren-owned, exact-request-bound, expiring/task-bounded, and one-time.

Minimum semantics:

```text
ApprovalId
authenticated owner principal binding
action identity
ProjectId + RepositoryId
normalized target/resource
security-relevant intent fingerprint
approved timestamp
expiry/task boundary
consumption/revocation state
```

Approval is atomically consumed before the first consequential executor attempt. Consumed/expired/mismatched/unknown/revoked approval fails closed. Independent retry after failure or ambiguity requires fresh approval.

## 9.5 Credential boundary

Write credentials:

- resolve only after policy + approval consumption;
- never enter BrainContext/model-visible action args/canonical state/memory/audit/owner-visible result;
- are referenced only by opaque write-specific purpose/ref;
- fail closed when missing/revoked;
- never silently fall back to broader credentials.

Read/write credential purposes remain logically separate.

## 9.6 Global read-only

A host-controlled fail-closed global read-only state must exist before the first write executor ships.

Absent/false/invalid write-enable configuration means read-only. In read-only mode no write executor runs and no write credential resolves.

## 9.7 Post-write verification + audit

Every write must verify intended external state by an independent read before returning success. Audit reconstructs proposal -> canonical target -> policy -> approval -> credential purpose -> execution -> verification without storing secrets.

## 9.8 v0.1 write scope

Allowed after M5 foundations are green:

```text
create non-default branch
controlled file/commit path on non-default branch
open pull request
```

Forbidden:

```text
write directly to default branch
merge PR
force push/history rewrite
delete repo/branch/data
repo admin/security changes
secret-management actions
production deploy
```

**Gate D PASSED. Gate D itself adds no external write capability.**

Approval binds repo/base/head/title/body digest or other security-relevant normalized parameters. Execute then fetch PR and verify repo/base/head/state/PR identity.

## M5 Slice 6 — End-to-end authorization/audit acceptance

Prove:

- approval non-replay across runs/actions;
- read-only kill blocks writes before credential resolution;
- revoked credential blocks previously approved intent;
- write secret never reaches brain/memory/audit/result;
- hostile repository/tool text cannot expand approval;
- uncertain external result is not reported successful without verification;
- complete audit can explain why the write happened.
