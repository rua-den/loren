# Loren v0.1 — Trustworthy Core Implementation Plan

**Status:** Active — M3 Canonical State  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002

v0.1 is not a feature-rich assistant release. It is the first version where Loren proves that identity, memory, action authorization, credentials, audit, and external tool use fit together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Build the smallest Loren that can reliably complete four end-to-end flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete regardless of how many integrations exist.

---

# 2. v0.1 non-goals

Explicitly defer:

- broad web research;
- reminders/background scheduling;
- Gmail/Calendar;
- voice/wake word;
- native mobile apps;
- Home Assistant;
- unrestricted shell/computer use;
- autonomous production deployments;
- multi-user product architecture;
- multi-agent orchestration;
- plugin marketplace;
- generic agent-framework capabilities;
- dynamic multi-provider routing as a release requirement.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
                         |            |
                         |       provider adapter
                         |            |
                         +---- ActionRequest
                                   |
                                   v
                            Action Gateway
                           /      |       \
                      Policy  Approval   Audit
                           \      |       /
                            Executor Boundary
                                   |
                             Secret Resolver
                                   |
                           GitHub / MCP / APIs
```

Hard invariant:

> **The brain can request an action. Only Loren can authorize and execute it.**

Changing brain provider must not migrate Loren identity, memory, permissions, projects, or audit history.

# 7. Milestone 3 — Canonical state and minimal world model [ACTIVE]

Implement only entities required by the v0.1 flows.

Longer-term minimum model:

```text
Owner
Project
Repository
MemoryRecord
PermissionRule
AuditEvent
```

M3 begins with the **Project/Repository identity and storage boundary only**. Memory and permission semantics are implemented in their dedicated milestones.

## M3 Slice 1 — Canonical identity + persistence

Build:

- stable `ProjectId` and `RepositoryId` owned by Loren;
- Project entity;
- Repository entity related to Project;
- normalized project aliases;
- GitHub owner/repository identity stored as integration metadata, never as Loren primary identity;
- timestamps;
- SQLite + EF Core production persistence;
- first production migration;
- repository/query boundary that keeps EF types outside `Loren.Core`.

Acceptance:

- save a Project/Repository/aliases;
- dispose/recreate persistence context;
- resolve the same canonical state after restart;
- no provider/runtime session ID is required.

## M3 Slice 2 — Deterministic alias resolution + prepared context

When explicitly configured:

```text
"wedding project"
"web đám cưới"
"wedding-online"
```

all resolve to the same canonical Project, whose Repository is `rua-den/wedding-online`.

The runtime should receive a small prepared Project/Repository context rather than raw database access.

## M3 Slice 3 — Gate C checkpoint

Before M4 expands memory, lock/document:

- canonical ID format/rules;
- schema migration policy;
- Project/Repository schema boundary;
- durable-memory source/trust classes;
- correction/supersession direction;
- memory versus audit deletion distinction;
- export format versioning approach.

A dedicated ADR is required if persistence becomes materially more complex than SQLite/EF Core.

## M3 requirements

- stable Loren IDs independent of GitHub/provider/runtime IDs;
- project aliases;
- Project -> Repository relation;
- timestamps and migrations;
- external/runtime/provider IDs only as integration metadata;
- no raw secret fields in canonical entities;
- provider conversation/session deletion must not delete Project/Repository state.

## M3 non-goals

Do not add `Person`, `Task`, `Decision`, `Preference`, or a broad/generic graph until a real product flow requires them.

## M3 exit gate

M3 is complete only when:

- canonical Project/Repository records survive restart;
- aliases resolve deterministically;
- external/provider identity is not used as the Loren primary key;
- runtime can consume prepared canonical project context without raw DB access;
- migration/ID/export/deletion decisions needed by Gate C are documented and accepted enough to begin M4.

# 8. Milestone 4 — Trusted memory

Implement continuity without creating an unstructured transcript dump.

Required memory source classes:

```text
OWNER_EXPLICIT
OWNER_CORRECTION
VERIFIED_TOOL
OWNER_APPROVED_INFERENCE
MODEL_INFERENCE
EXTERNAL_CONTENT
```

Trust rules:

- owner correction supersedes previous current truth;
- tool facts keep source and verification timestamp;
- model inference is not owner truth;
- external content is untrusted;
- external content cannot silently create owner preference, permission, policy, credential metadata, or authoritative personal state;
- promotion to trusted durable state is explicit or deterministic and inspectable.

Minimum capabilities: save, scope, provenance, inspect, correct/supersede, forget/delete, retrieval by entity/text/recency/authority, and small inspectable brain context.

M4 exit requires restart continuity, correction, and memory-poisoning tests to pass before GitHub writes are enabled.

---

# 9. Milestone 5 — Action policy, credentials, and GitHub writes

This milestone opens Loren's first real side-effect boundary.

```text
Brain / Runtime
 -> ActionRequest (no secret)
 -> Action Gateway
 -> allow / deny / require approval
 -> Controlled Executor
 -> Secret Resolver
 -> GitHub
 -> post-verification
 -> Audit
```

v0.1 write scope is narrow: create branch, create/update file/commit path, commit, open pull request.

Explicitly not required: merge main, force push, repo deletion, history rewrite, admin/security settings, production deploy.

Before the first live write, Gate D must settle credential mechanism/location/scope/redaction/rotation and approval binding/replay behavior.

M5 adversarial acceptance includes cross-repo/action approval replay rejection, prompt-injection resistance, global read-only enforcement, and fail-closed ambiguous authorization.

- current Project context;
- memory inspect/correct/delete;

---

# 11. Milestone 7 — Recovery and state ownership proof

Export minimum:

- owner/Loren continuity configuration;
- Projects/Repositories;
- durable memory/provenance;
- permission rules;
- audit according to retention policy;
- schema/export version metadata.

Secrets must not be exported as plaintext canonical state.

Acceptance:

```text
create project + memory + policy
-> export
-> wipe canonical DB
-> restore
-> restart Loren
-> same project alias/memory/policy works
```

Provider/runtime conversation state must not be required for recovery.

---

# 12. Milestone 8 — Security and reliability E2E

Minimum suite covers restart continuity, aliases, memory correction/poisoning, GitHub grounding, authorized/approval-gated writes, denied destructive requests, prompt injection, approval replay, global read-only mode, duplicate/retry protection, stale-state checks, provider/tool failures, credential/log redaction, cancellation/turn limits, export/restore, and audit reconstruction.

Reliability requirements include bounded retries/model/tool loops, cancellation propagation, correlated IDs, write postconditions, safe privileged-state handling after crashes, and provider-session-independent canonical state.

---

# 13. v0.1 release gate

Tag `v0.1.0` only when all are true:

- four required release flows pass end to end;
- ADR-001 and ADR-002 are Accepted;
- external operational answers are tool-grounded;
- memory survives restart and owner correction;
- untrusted external content cannot promote itself to trusted policy;
- brain/runtime cannot bypass ActionGateway;
- write credentials resolve only inside controlled executor boundary;
- approvals are concrete and non-replayable;
- consequential writes are post-verified;
- canonical export/wipe/restore passes;
- important actions/memory mutations are auditable;
- deterministic core/runtime tests run without live model behavior;
- CI/static checks are green;
- known limitations are documented.
