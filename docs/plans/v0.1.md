# Loren v0.1 — Trustworthy Core Implementation Plan

**Status:** Active — M4 Trusted Durable Memory  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002  
**Canonical state/memory lifecycle:** ADR-003

v0.1 is not a feature-rich assistant release. It is the first version where Loren proves that identity, memory, action authorization, credentials, audit, and external tool use fit together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Build the smallest Loren that can reliably complete four end-to-end flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete regardless of how many integrations exist.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
      |                  |            |
      |                  |       provider adapter
      |                  |            |
      |                  +---- ActionRequest
      |                              |
      |                              v
      |                       Action Gateway
      |                      /      |       \
      |                 Policy  Approval   Audit
      |                      \      |       /
      |                       Executor Boundary
      |                              |
      |                        Secret Resolver
      |                              |
      |                        GitHub / MCP / APIs
      |
      +--> Loren-owned canonical state
            Project / Repository
            Durable Memory + provenance
            Permission rules
            Audit history
```

Hard invariants:

> **The brain can request an action. Only Loren can authorize and execute it.**

> **The brain can consume prepared memory. It cannot silently promote model/external content into trusted owner truth.**

Changing brain provider must not migrate Loren identity, memory, permissions, projects, or audit history.

# 8. Milestone 4 — Trusted durable memory [ACTIVE]

M4 implements continuity without an unstructured transcript dump and without allowing model/external text to become trusted owner state by accident.

## M4 Slice 1 — Canonical MemoryRecord + OWNER_EXPLICIT persistence [CURRENT]

First vertical slice:

```text
Owner explicitly asks Loren to remember a durable fact
        |
        v
OWNER_EXPLICIT MemoryRecord
        |
        +--> Loren-owned MemoryRecordId
        +--> scope / subject refs
        +--> provenance + timestamps
        |
        v
SQLite / EF Core
        |
restart
        |
        v
trusted current-memory retrieval
```

Implement the minimum model needed to prove durable owner memory:

- Loren-owned `MemoryRecordId`;
- canonical `MemoryRecord` model in `Loren.Core`;
- explicit source class from ADR-003;
- text/content payload appropriate for the first slice;
- Project/Repository scope references where applicable;
- creation/update timestamps;
- provenance/source reference fields sufficient for `OWNER_EXPLICIT`;
- lifecycle representation that can support current/superseded state without destructive overwrite;
- EF-neutral memory store/query boundary in `Loren.Core`;
- SQLite/EF implementation and checked-in migration in `Loren.Infrastructure`;
- real SQLite save -> dispose -> restart -> retrieve acceptance test;
- retrieval must return the same Loren memory ID and source authority after restart.

Slice 1 must not require a model/provider session to preserve or retrieve memory.

## M4 Slice 2 — Owner correction + supersession

Prove:

```text
Memory A current
 -> owner correction
 -> Memory B current
 -> A superseded_by B
```

Requirements:

- `OWNER_CORRECTION` is explicit;
- current-truth queries exclude superseded records by default;
- history remains reconstructable while retained;
- correction does not mutate the old claim into a different claim;
- model/external content cannot supersede owner-authoritative state.

## M4 Slice 3 — Authority-aware retrieval + prepared memory context

Prepare a small inspectable memory package for runtime rather than exposing the database.

Requirements:

- retrieve by canonical subject/scope and textual relevance needed by current flows;
- rank/filter by authority and current lifecycle state;
- preserve provenance in application-visible structures;
- only a bounded prepared context reaches `AgentLoop` / `IBrain`;
- no EF/DbContext types cross into runtime/brain;
- external/tool facts carry verification/source semantics instead of masquerading as owner truth.

## M4 Slice 4 — Forget/delete semantics

Implement owner-controlled forgetting consistent with ADR-003:

- deleted memory disappears from future retrieval/context;
- memory deletion does not cascade-delete ordinary audit history;
- retained audit minimizes sensitive payload;
- deletion behavior is deterministic and tested after restart.

## M4 Slice 5 — Poisoning / trust-boundary acceptance

Adversarially prove that:

- `MODEL_INFERENCE` is not owner truth;
- `EXTERNAL_CONTENT` cannot create owner preference/policy/permission;
- `VERIFIED_TOOL` is authoritative only for the verified external fact/time;
- `OWNER_APPROVED_INFERENCE` requires explicit owner approval;
- owner correction wins for current owner truth in its scope.

## M4 exit gate

M4 is complete only when:

- owner-explicit memory survives restart;
- provenance/source class survives restart;
- correction/supersession returns only current truth by default while preserving history;
- owner forget/delete removes memory from retrieval without pretending audit was ordinary memory;
- prepared runtime context remains small and inspectable;
- hostile/model/external content cannot silently become trusted owner state;
- all deterministic tests and repository CI gates are green.

# 9. Milestone 5 — Action policy, credentials, and GitHub writes

First real side-effect boundary:

```text
Brain / Runtime
 -> ActionRequest (no secret)
 -> Action Gateway
 -> allow / deny / require approval
 -> Controlled Executor
 -> Secret Resolver
 -> GitHub
 -> post-verification
 -> Audit
```

v0.1 write scope remains narrow: create branch, create/update file/commit path, commit, and open pull request. **Gate D must settle credential and approval binding/replay rules before the first real write path is enabled.**

# 11. Milestone 7 — Recovery and state ownership proof

Export minimum includes owner continuity config, Projects/Repositories, durable memory/provenance, permission rules, retained audit, and schema/export version metadata. Secrets are excluded.

Acceptance:

```text
create canonical project + memory + policy
 -> logical export format_version 1
 -> wipe canonical DB
 -> restore into current migrated schema
 -> restart Loren
 -> same canonical IDs and behavior
```

Provider/runtime conversation state must not be required for recovery.

---

# 12. Milestone 8 — Security and reliability E2E

Cover restart continuity, aliases, memory correction/poisoning, GitHub grounding, authorized/approval-gated writes, denied destructive requests, prompt injection, approval replay, global read-only mode, duplicate/retry protection, stale-state checks, provider/tool failures, credential/log redaction, cancellation/turn limits, export/restore, and audit reconstruction.
