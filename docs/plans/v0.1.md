# Loren v0.1 — Trustworthy Core Implementation Plan

**Status:** Active — Gate D before M5 Action/Credential Boundary  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002  
**Canonical state/memory lifecycle:** ADR-003

v0.1 is the first version where Loren must prove identity, memory, action authorization, credentials, audit, and external tool use can work together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Required flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete.

---

# 2. v0.1 non-goals

Defer broad web research, reminders/background scheduling, Gmail/Calendar, voice, native mobile apps, Home Assistant, unrestricted shell/computer use, autonomous production deployments, multi-user architecture, multi-agent orchestration, plugin marketplace, generic framework features, and dynamic multi-provider routing as a release requirement.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
      |                  |            |
      |                  |       provider adapter
      |                  |            |
      |                  +---- ActionRequest
      |                              |
      |                              v
      |                       Action Gateway
      |                      /      |       \
      |                 Policy  Approval   Audit
      |                      \      |       /
      |                       Executor Boundary
      |                              |
      |                        Secret Resolver
      |                              |
      |                        GitHub / MCP / APIs
      |
      +--> Loren-owned canonical state
            Project / Repository
            Durable Memory + provenance
            Permission rules
            Audit history
```

Hard invariants:

> **The brain can request an action. Only Loren can authorize and execute it.**

> **The brain can consume prepared memory. It cannot silently promote model/external content into trusted owner truth.**

## M4 Slice 4 — Forget/delete semantics [COMPLETE]

PR #21 merged at `87b5a39ccae7c931de9668fed5283a4742be73f7`.

Evidence: implementation CI #133 / `33865419023`, final exact-head CI #137 / `33865716479` — PASS.

```text
A -> B -> C(current)
 -> ForgetAsync(C)
 -> validate current target
 -> reverse-walk same-scope linear correction chain
 -> delete A -> B -> C in one SQLite transaction
 -> restart
 -> no forgotten chain record exists or reaches prepared context
```

Whole-chain purge prevents corrected old claims from resurrecting. Malformed/stale/unknown operations fail closed. Unrelated memory survives. Forgetting is separate from audit retention and does not use a generic audit cascade.

## M4 Slice 5 — Poisoning / trust-boundary acceptance [COMPLETE]

PR #22 closes the M4 trust gate.

Production hardening:

- trusted prepared-context records require non-empty provenance;
- provenance/source references are independently bounded;
- the whole serialized memory payload — content, provenance, IDs, scope, timestamps — is inert data, never instruction, permission, policy, or action authorization;
- `MODEL_INFERENCE` and `EXTERNAL_CONTENT` remain excluded even with owner-looking provenance;
- `OWNER_APPROVED_INFERENCE` and `VERIFIED_TOOL` require provenance;
- `VERIFIED_TOOL` does not automatically represent current external state or grant owner permission.

Adversarial acceptance proves:

- spoofed model/external records cannot enter trusted prepared context;
- unproven approved-inference/tool records are excluded;
- owner-approved inference remains distinguishable from unapproved model inference;
- owner correction wins current owner truth while superseded/conflicting low-authority records stay out;
- malicious provenance text is bounded and treated as data;
- `MODEL_INFERENCE` cannot use the owner-correction boundary;
- a normal `LorenRunService` turn reads prepared memory without calling `AddAsync`, `CorrectAsync`, or `ForgetAsync`.

CI #140 / run `33866182751` passed restore, zero-warning build, all tests, format, secret scan, dependency scan and web/auth smoke after two earlier wording assertions tightened the final safety framing.

## M4 exit gate [PASSED]

M4 now proves:

- owner-explicit memory survives restart with canonical identity/provenance;
- owner correction appends/supersedes without destructive content rewrite;
- current retrieval excludes superseded claims;
- owner forget purges the full correction chain and stays forgotten after restart;
- runtime/brain receive a bounded inspectable prepared package rather than DB access;
- low-authority model/external content cannot silently become trusted owner state;
- ordinary runtime turns do not silently mutate durable memory;
- memory forgetting and audit retention remain separate;
- deterministic tests work without a live model.

# 9. Gate D — Action/Credential Policy [NEXT]

Gate D must pass before the first real external write path is enabled.

It must settle:

- exact write action contracts and policy dimensions;
- approval binding to action/target/parameters and non-replay semantics;
- write credential storage/resolution and read/write separation;
- secret redaction, rotation, and revocation;
- global read-only / kill behavior;
- post-write verification and audit expectations.

No write-capable integration may ship before this gate passes.

---

# 10. Milestone 5 — Action policy, credentials, and narrow GitHub writes [AFTER GATE D]

Allowed narrow v0.1 write set:

- create branch;
- create/update file content or equivalent commit path;
- create commit;
- open pull request.

Out of scope for v0.1 writes:

- merge main;
- force push;
- delete repository;
- rewrite history;
- repository admin/security changes;
- production deploy.

Acceptance requires Loren policy authorization, controlled credential resolution, scoped/non-replayable approval where needed, post-write verification, and correlated audit.
