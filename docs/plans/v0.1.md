# Loren v0.1 — Useful Trustworthy Assistant Plan

**Status:** Active — roadmap rebaselined 2026-09-06  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002  
**Canonical state/memory lifecycle:** ADR-003  
**Action/approval/credential boundary:** ADR-004  
**Current slice:** `M6A.2 — Current-information / web read`

v0.1 is the first version that should feel like an actual personal secretary rather than a collection of infrastructure components.

> **Loren must converse, remember, retrieve current information, research, and organize before we broaden external mutation capabilities.**

---

# 1. v0.1 objective

The owner should be able to keep Loren open and use it naturally throughout the day for questions, current information, project context, memory, lightweight organization, and a very small number of explicitly approved actions.

Required interaction classes:

```text
A. ordinary conversation / reasoning
B. current information lookup
C. project/personal context recall
D. research and synthesis with sources
E. notes / decisions / tasks
F. one explicitly approved consequential action
G. explanation/audit of what Loren did
```

---

# 2. Required owner-visible flows

## Flow 1 — ordinary conversation

```text
Owner: "Giải thích cái này cho tao dễ hiểu."
Loren: answers directly from the brain when no external fact is required.
```

## Flow 2 — current information

```text
Owner: "Tìm giúp tao thông tin mới nhất về X."
Loren:
 -> recognizes model knowledge may be stale
 -> uses read-only information/search tool
 -> returns grounded answer + sources
```

## Flow 3 — personal/project context

```text
Owner: "Project Loren hiện sao rồi?"
Loren:
 -> resolves canonical project
 -> uses trusted memory
 -> reads live external state when necessary
 -> answers naturally
```

## Flow 4 — durable memory

```text
Owner: "Nhớ rằng production deploy phải hỏi tao."
 -> durable trusted memory
 -> restart
Owner: "Rule deploy của tao là gì?"
 -> correct current answer
```

## Flow 5 — research

```text
Owner: "Research 3 lựa chọn cho tao, đưa trade-off và nguồn."
 -> bounded retrieval
 -> multiple sources
 -> source-aware synthesis
 -> distinguish sourced facts from inference
```

## Flow 6 — personal organization

```text
Owner: "Ghi decision này lại."
Owner: "Tạo task review auth flow."
Owner: "Project Loren còn task nào?"
Owner: "Đánh dấu task review auth flow xong."
```

This is durable Loren-owned state. Scheduled delivery/reminders are deferred until Gate E.

## Flow 7 — approved action through conversation

```text
Owner: "Tạo branch abc cho Loren."
 -> brain proposes typed action
 -> Loren resolves canonical target
 -> owner sees exact proposed action
 -> owner explicitly approves
 -> Gate D executes
 -> post-write verification
 -> Loren explains result
```

## Flow 8 — explain what happened

```text
Owner: "Tại sao mày vừa làm việc đó?"
 -> reconstruct request
 -> context
 -> tool facts
 -> policy
 -> approval
 -> credential purpose
 -> execution
 -> verification
 -> outcome
```

# 3. v0.1 non-goals

Not required for the first useful release:

```text
voice/STT/TTS
mobile native app
Home Assistant
unrestricted shell/computer use
autonomous production deployments
multi-user architecture
multi-agent orchestration
standing write permissions
broad background autonomy
```

Calendar/Gmail may begin in v0.1 only if a read-only vertical slice is cheap and materially improves the owner checkpoint, but they are primarily v0.2 personal-secretary integrations.

# 4. Architecture target

```text
Owner conversation
      |
      v
ASP.NET Core host / owner UI
      |
      +--> canonical context builder
      |       Project / Repository / Memory / Organization
      |
      v
Loren Runtime
      |
      +--> IBrain
      |
      +--> read-only information tools
      |       web search/fetch/current facts
      |       GitHub read
      |       later personal connectors
      |
      +--> ActionGateway for consequential actions
              policy
              approval
              credential boundary
              executor
              verification
              audit
```

Hard invariants:

> **Retrieved information is data, not authority.**

> **The brain can request actions; only Loren authorizes and executes them.**

> **Authentication is not write approval.**

> **A write is not successful until Loren verifies the intended postcondition.**

## M6A.2 — Read-only current-information action [ACTIVE — PR #30]

Current implementation introduces read-only `web.search` backed by Ollama Web Search.

```text
query
 -> ActionGateway READ policy
 -> Ollama web search
 -> bounded response
 -> validated URL/title/content
 -> untrusted evidence marker
 -> BrainActionObservation
 -> sourced final answer
```

Requirements already implemented in PR #30:

- uses existing `OLLAMA_API_KEY`;
- no new write capability;
- bounded query/source count/content;
- invalid/overlong source URLs are excluded rather than truncated into broken citations;
- missing credential fails before external request;
- external failure body/secret is not surfaced;
- deterministic fake-provider executor tests;
- deterministic agent-loop test proving search -> evidence -> sourced final output;
- production conversation exposes `github.read_repository` + `web.search` as read tools.

Close M6A.2 only after exact-head PR CI and post-merge `main` are green.

## M6A.3 — Source-aware research/synthesis [NEXT]

# 8. Resume narrow write workflow after interaction checkpoint

## M5 Slice 4 — controlled file/commit path

Approval binds canonical repo, non-default branch, path, content digest, and relevant commit metadata. Post-write verification checks commit identity, branch ref, and file/content identity.

## M5 Slice 5 — open pull request

Approval binds repo/base/head/title/body digest/security-relevant parameters. Fetch PR after creation and verify repo/base/head/state/identity.

## M5 Slice 6 — write authorization/audit E2E

Replay, read-only kill, revoked credential, prompt injection, ambiguous external result, redaction, audit reconstruction.

---

# 9. Recovery closeout

Logical export `format_version = 1` must restore Projects/Repositories, trusted durable Memory, Notes/Decisions/Tasks, appropriate approval state, retained audit, and canonical IDs. Never export raw credentials.

---

# 10. Security/reliability E2E

Cover restart continuity, aliases, memory lifecycle/poisoning, retrieved-content prompt injection, stale/current-info failure behavior, grounded external facts, approval replay, credential revocation/redaction, read-only kill, cancellation, provider/tool failure, write post-verification, export/restore, and audit reconstruction.

---

# 11. v0.1 release gate

Tag `v0.1.0` only when:

- the owner primarily interacts through natural conversation;
- stable questions work through the brain;
- current questions use external read tools instead of stale guessing;
- research is source-aware;
- trusted memory survives restart/correction/forget;
- basic notes/decisions/tasks are durable and usable from conversation;
- project context combines canonical state + memory + authoritative reads;
- at least one consequential action follows conversational proposal -> explicit approval -> execute -> verify -> explain;
- write credentials never leak;
- read-only and revocation stop writes;
- recovery succeeds;
- core logic remains deterministic-testable without live provider behavior.
