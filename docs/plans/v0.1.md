v0.1 is the first version where Loren must prove identity, memory, action authorization, credentials, audit, and external tool use can work together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Required flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete.

# 2. v0.1 non-goals

Defer broad web research, reminders/background scheduling, Gmail/Calendar, voice, native mobile apps, Home Assistant, unrestricted shell/computer use, autonomous production deployments, multi-user architecture, multi-agent orchestration, plugin marketplace, generic framework features, and dynamic multi-provider routing as a release requirement.

## M4 Slice 2 — Owner correction + supersession [IMPLEMENTED / PR #19 FINAL GATE]

PR #19 implements explicit owner correction semantics:

```text
Memory A current
 -> CorrectAsync(A, OWNER_CORRECTION B)
 -> append B
 -> A.SupersededById = B.Id
 -> commit both lifecycle changes atomically
 -> current query returns B only
 -> history can still reconstruct A -> B
```

Implementation properties:

- `IMemoryStore.CorrectAsync(currentMemoryRecordId, correction)` is explicit; no generic destructive content-update API exists;
- replacement source must be `OWNER_CORRECTION`;
- replacement must use a new `MemoryRecordId` and begin current;
- target must exist and must still be current;
- correction must preserve the exact Project/Repository scope;
- correction timestamp cannot move backward relative to the current lifecycle timestamp;
- correction ID cannot already exist;
- replacement insert and old-record supersession are inside one SQLite transaction;
- old content is never rewritten;
- `ListCurrentForProjectAsync` excludes superseded records by default.

Real SQLite acceptance tests prove:

- OWNER_EXPLICIT -> OWNER_CORRECTION chain survives restart;
- old content and old canonical ID remain reconstructable;
- old record's `SupersededById` points to the correction;
- correction remains current with `OWNER_CORRECTION` authority + owner provenance;
- default current query returns only the correction;
- `MODEL_INFERENCE` cannot be submitted through the correction boundary;
- changed-scope correction fails without partial insert;
- stale/already-superseded target cannot be corrected again and leaves no replacement record.

Implementation CI #119 / run `33861345949`: **PASS** for restore, zero-warning build, tests, format, secret scan, dependency scan, and web/auth smoke.

Slice 2 remains open until the documentation-synchronized final PR head passes exact-head CI and PR #19 merges.
