# Loren v0.1 — Trustworthy Core Implementation Plan

**Status:** Active — M4 Trusted Durable Memory  
**Parent plan:** `docs/plans/master-plan.md`  
**Architecture boundary:** ADR-001  
**Accepted stack:** ADR-002  
**Canonical state/memory lifecycle:** ADR-003

v0.1 is not a feature-rich assistant release. It is the first version where Loren proves that identity, memory, action authorization, credentials, audit, and external tool use fit together safely enough to become a real daily-use foundation.

---

# 1. v0.1 objective

Build the smallest Loren that can reliably complete four end-to-end flows:

```text
1. "Loren, repo wedding hiện sao rồi?"
   -> resolve project/repository
   -> read current GitHub state
   -> answer from structured tool data

2. "Nhớ rằng project này production deploy phải hỏi tao."
   -> save trusted owner-provided memory/policy
   -> restart Loren
   -> retrieve the same current rule later

3. "Tạo branch và chuẩn bị thay đổi X."
   -> brain requests action
   -> Loren validates and authorizes
   -> controlled executor resolves credential
   -> GitHub write
   -> verify resulting state
   -> audit result

4. "Tại sao mày vừa làm việc đó?"
   -> reconstruct context, action request, policy decision,
      approval, execution, verification, and outcome
```

If these four flows are not trustworthy, v0.1 is not complete regardless of how many integrations exist.

---

# 2. v0.1 non-goals

Explicitly defer broad web research, reminders/background scheduling, Gmail/Calendar, voice/wake word, native mobile apps, Home Assistant, unrestricted shell/computer use, autonomous production deployments, multi-user product architecture, multi-agent orchestration, plugin marketplace, generic agent-framework capabilities, and dynamic multi-provider routing as a release requirement.

# 3. Architecture target

```text
Owner / Web UI
      |
      v
ASP.NET Core Host
      |
      v
Context Builder -> Loren Runtime -> IBrain
      |                  |            |
      |                  |       provider adapter
      |                  |            |
      |                  +---- ActionRequest
      |                              |
      |                              v
      |                       Action Gateway
      |                      /      |       \
      |                 Policy  Approval   Audit
      |                      \      |       /
      |                       Executor Boundary
      |                              |
      |                        Secret Resolver
      |                              |
      |                        GitHub / MCP / APIs
      |
      +--> Loren-owned canonical state
            Project / Repository
            Durable Memory + provenance
            Permission rules
            Audit history
```

Hard invariants:

> **The brain can request an action. Only Loren can authorize and execute it.**

> **The brain can consume prepared memory. It cannot silently promote model/external content into trusted owner truth.**

Changing brain provider must not migrate Loren identity, memory, permissions, projects, or audit history.

## M4 Slice 1 — Canonical MemoryRecord + OWNER_EXPLICIT persistence [IMPLEMENTED / PR #18 FINAL GATE]

PR #18 implements the minimum durable-memory persistence boundary:

```text
OWNER_EXPLICIT durable fact
        |
        v
MemoryRecord + MemoryRecordId
        |
Project / Repository scope + provenance
        |
        v
EF-neutral IMemoryStore
        |
SQLite / EF Core migration
        |
restart
        |
        v
same canonical memory ID + authority + scope
```

Implemented:

- Loren-owned `MemoryRecordId` using the canonical lowercase GUID `N` representation;
- canonical `MemoryRecord` in `Loren.Core`;
- explicit `MemorySourceClass` covering all six ADR-003 authority/source classes;
- content, Project/Repository scope, source reference/provenance, timestamps, and `SupersededById` lifecycle representation;
- domain invariants for valid scope, non-self-supersession, and timestamp ordering;
- EF-neutral `IMemoryStore` limited to `AddAsync`, `GetAsync`, and `ListCurrentForProjectAsync`;
- no generic content update API, so future corrections cannot silently overwrite an existing claim;
- canonical `MemoryRecords` SQLite schema;
- explicit migration `202609040002_AddMemoryRecords`;
- Project, Repository, and self-supersession foreign keys using restrictive deletion behavior;
- `SqliteMemoryStore` exact source-class persistence mapping;
- fail-closed validation that repository-scoped memory uses a Repository belonging to the same Project;
- scoped production DI registration;
- Core invariant tests;
- real SQLite save -> dispose/restart -> retrieve acceptance test.

Acceptance verifies that an `OWNER_EXPLICIT` record with `owner:authenticated` provenance retains the same `MemoryRecordId`, source authority, Project/Repository scope, content, timestamps, and current lifecycle state after restart.

CI evidence:

- CI #112 / run `33860545089`: zero-warning production build passed; integration test exposed SQLite `DateTimeOffset` ordering translation limitation;
- fix commit `15bbecd078bbf04f012464673cd856353b6ea84c`: filter in SQLite, materialize, then deterministic client-side ordering;
- implementation CI #113 / run `33860641367`: **PASS** across restore, build, tests, format, secret scan, dependency scan, and web/auth smoke.

The Slice 1 capability is implemented, but **not closed** until the documentation-synchronized final PR head passes exact-head CI and PR #18 merges.

- automatic model-driven memory promotion.

## M4 Slice 2 — Owner correction + supersession [NEXT]

Prove:

```text
Memory A current
 -> explicit owner correction
 -> Memory B current / OWNER_CORRECTION
 -> A.superseded_by = B
 -> default current query excludes A
 -> retained history still reconstructs A -> B
```

Requirements:

- correction is an explicit append + lifecycle mutation, not a generic destructive content update;
- replacement scope is validated against the record being corrected;
- only a current record can be superseded;
- correction and supersession update are transactional;
- current-truth queries exclude superseded records by default;
- history remains reconstructable while retained;
- model/external content cannot supersede owner-authoritative state.

## M4 Slice 3 — Authority-aware retrieval + prepared memory context

Prepare a bounded, inspectable memory package for runtime rather than exposing the database. Retrieval must respect canonical subject/scope, lifecycle, authority and provenance; EF/DbContext types never cross into runtime/brain.

## M4 Slice 4 — Forget/delete semantics

Owner-controlled forgetting must remove memory from future retrieval/context without pretending audit is ordinary memory or silently cascading audit deletion.

## M4 Slice 5 — Poisoning / trust-boundary acceptance

Adversarially prove that MODEL_INFERENCE and EXTERNAL_CONTENT cannot become owner truth/policy, VERIFIED_TOOL is authoritative only for the verified fact/time, OWNER_APPROVED_INFERENCE requires explicit approval, and owner correction wins for current owner truth in scope.

## M4 exit gate

M4 is complete only when owner-explicit memory survives restart; provenance survives; correction/supersession preserves history while returning only current truth by default; forget/delete works according to ADR-003; prepared context is bounded/inspectable; hostile/model/external content cannot silently become trusted owner state; and all repository CI gates are green.
